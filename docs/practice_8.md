# Письменные ответы по работе 8

## 1. Приложение в контейнере принимает соединения на адресе 127.0.0.1:<порт>, порт опубликован как 127.0.0.1:<порт>:<порт>. Почему обращение с сервера завершается ошибкой? Почему адрес 0.0.0.0 внутри контейнера не делает приложение доступным из сети?

Процесс слушает только loopback контейнера, а DNAT доставляет на его сетевой интерфейс, поэтому соединение не принимается. Нужен bind 0.0.0.0:8002 внутри контейнера. Внешнюю доступность определяет публикация хоста 127.0.0.1:8002:8002, а не внутренняя wildcard-привязка.

## 2. Файл .env удалён из репозитория отдельным коммитом. Можно ли считать пароль из шаблона секретным? Что нужно сделать с паролем и что можно сделать с историей, учитывая, что ветка main уже опубликована (ПР № 3)?

Удалённый .env остаётся в старых коммитах и исходный пароль считается раскрытым. На сервере создан новый независимый случайный пароль. Историю можно согласованно переписать filter-repo и принудительно обновить ссылки, но это нарушает работу чужих клонов; уже опубликованный секрет всегда сначала заменяют. В работе сохранена исходная main шаблона и его неиспользуемый пароль.

## 3. Почему секрет нельзя удалить из образа, добавив в конец Dockerfile инструкцию RUN rm .env? Чем это опасно при публикации образа в реестр (ПР № 10)?

Удаление создаёт новый слой и не стирает файл из предыдущего. Пользователь реестра может извлечь слой с секретом. Исключение из контекста через .dockerignore предотвращает его попадание в образ; копирование только нужных файлов усиливает это свойство.

## 4. Почему CMD записывается в exec-форме? Как определить, какой процесс в контейнере имеет PID 1?

Exec-форма запускает gunicorn непосредственно как PID 1 и доставляет ему SIGTERM. Shell-форма добавляет /bin/sh -c, который может не передать сигнал. Проверить docker top или docker exec с чтением /proc/1/cmdline; остановка исправленного тестового контейнера измеряется time docker stop.

## 5. Кто и в какой момент подставляет значения ${REDIS_PASSWORD} и $$REDIS_PASSWORD в docker- compose.yml? Что изменится, если в проверке готовности записать ${REDIS_PASSWORD}?

${REDIS_PASSWORD} подставляет Compose на сервере из окружения оболочки или .env до создания контейнера. $$ сохраняет знак $, затем переменную раскрывает оболочка CMD-SHELL внутри контейнера из env_file. Если использовать ${...} в healthcheck, значение попадёт в готовую конфигурацию; экспортированная переменная может разойтись с env_file. Секрет не экспортируется в рабочей оболочке.

## 6. Почему команда сервиса redis начинается с redis-server, а не с sh -c "redis-server …"? Как проверить, от имени какого пользователя работает Redis?

Точка входа официального образа распознаёт redis-server и при старте от root меняет владельца данных и понижает привилегии до redis. sh -c обходит эту ветку. Проверить docker compose top и фактический UID процесса через /proc или ps; пользователь утилиты docker exec сам по себе не доказывает пользователя основного процесса.

## 7. Порт Redis не опубликован. Зачем в таком случае пароль? Кто может обратиться к Redis?

К Redis могут обращаться приложение и другие участники сети backend, а также администратор Docker. Непубликация изолирует от внешней сети, пароль ограничивает использование протокола доступными участниками; он не защищает от администратора с root.

## 8. Чем depends_on с условием service_healthy отличается от depends_on без условия? Что увидит пользователь в первые секунды после запуска при отсутствии условия?

service_healthy ждёт PONG с правильным паролем. Обычный depends_on ждёт только запуск контейнера. Без ожидания первые запросы могли бы завершиться 500 из-за отказа подключения или ещё неготового Redis.

## 9. Что произойдёт с данными после docker compose down, после docker compose down -v и после замены тега образа на redis:latest?

down сохраняет именованный том и hits. down -v удаляет его и данные, поэтому в КР не выполняется. redis:latest допускает неожиданную смену основной версии, изменение формата AOF и поведения; закрепление 7-alpine снижает этот риск, но требует контролируемых обновлений.

## 10. Зачем для <имя>.devops.local выпущен отдельный сертификат? Что выведет curl --cacert ~/devops.crt https://<имя>.devops.local и почему? Как Nginx выбирает сертификат, если на порту 443 описано несколько блоков server?

Сертификат devops.local не содержит notes.devops.local и имеет другую подпись. curl --cacert ~/devops.crt к notes отклонит сертификат нового ресурса из-за отсутствия доверия, а даже общий ключ без SAN нового имени привёл бы к ошибке имени. Nginx выбирает TLS-конфигурацию по SNI, переданному до HTTP-запроса.

## 11. Какое значение выводится в строке client ответа /whoami? Почему приложение не может определить адрес клиента по TCP-соединению? Почему значению X-Forwarded-For, полученному напрямую от клиента, доверять нельзя?

client содержит адрес хоста, который видел Nginx, из X-Real-IP. TCP-соединение приложения приходит от обратного прокси через Docker, поэтому его peer не равен исходному браузеру. Прямо присланный клиентом X-Forwarded-For может быть подделан; доверять следует только известным прокси и корректно настроенной цепочке.

## 12. Что произойдёт со всеми ресурсами стенда после sudo reboot? Какие службы и контейнеры запустятся автоматически, какие нет и почему?

После reboot запускаются включённые systemd-службы ssh, nginx, docker и ufw. Compose-контейнеры с unless-stopped стартуют, если не были остановлены вручную; разовые тестовые контейнеры без restart не стартуют. Необходимо также запустить саму VM после перезагрузки Mac.

## 13. Почему запись в файле hosts нужна на хостовой системе и не нужна на сервере для работы обратного прокси-сервера?

Имя нужно клиенту для получения адреса перед TCP/TLS. Nginx получает Host и SNI и использует явно заданный upstream 127.0.0.1:8002, поэтому для этих действий DNS-запись notes на самом сервере не требуется.

## 14. Порт приложения ошибочно опубликован как "<порт>:<порт>". Почему UFW не препятствует доступу из сети? Обнаружит ли это проверка раздела [5] сценария аудита из ПР № 7? Какую проверку нужно добавить?

Публикация без адреса делает порт доступным на всех интерфейсах через Docker DNAT/FORWARD в обход обычного UFW INPUT. Раздел [5] проверяет только 5000 и 5432, поэтому 8002 он не обнаружит. Добавлен раздел [6] с docker compose port app 8002 и точным сравнением с 127.0.0.1:8002.
